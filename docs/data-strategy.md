# Geography data strategy

## Fixed geography

Use a flat equirectangular (Plate Carrée) 2D map with equal longitude/latitude steps and a time-agnostic hierarchy: location → province → area → region → subcontinent → continent. Use reasonably recent reliable administrative sources, older where needed; record dates, but require no common reference year. Freeze chosen footprints across history. Start with six land continents excluding Antarctica plus ocean groups. Approve each top-down subdivision before child work (17 subcontinents is illustrative); check lower-level boundaries fit and flag important inhabited-island exceptions at the first continent review.

Within map coverage, no land is permanently excluded or impassable: sparse regions remain ordinary locations with proportionate research and may be larger without an imposed size. Every included cell belongs to exactly one land or non-river-water location. Land-continent groups include nearby seas, island-region waters, and lakes; Pacific, Atlantic, Indian, and Arctic groups cover remaining waters. Oceania may include broad waters around remote islands; large seas may split; Chukchi has Arctic ancestry. Non-river waters are named and selectable. Small lakes/islands may disappear; no lake overlay. Assign each cell to its greatest-overlap location. For mixed cells, first choose land/water by covered area (land wins exact ties), then greatest-overlap location within that type; stable location IDs break ties. Investigate source gaps/overlaps and document approximation rules and consequences.

Use equal equirectangular steps of 0.02197265625°. The 16,384 × 8,192 full-world reference grid cropped at nominal 60°S and retaining 90°N row-aligns to 16,384 × 6,827 cells (111,853,568), southern edge 60.00732421875°S. Store one canonical losslessly compressed grid, initially unpartitioned. Unsigned 16-bit values are location IDs directly, not mapping codes; reserve 0 during construction (65,535 usable IDs), widen to 32-bit if needed, and impose no research cap. Every published cell is assigned; compression size is unmeasured.

## Evidence, research, review, and app data

1. **Evidence:** R2 stores original sources of any size; Neon tracks references, dates, and checksums without duplicate copies.
2. **Editable geography:** Neon/PostGIS stores stable numeric ID, name, level, parent, polygon, and (for locations) land/water type. Versioned parent proposals retain sources, reasoning, and review status. River records store stable ID, name, line, and sources.
3. **Generated geography:** code derives approved hierarchy/names, app tables, and river display/selection data in Neon; R2 stores the canonical cell-ID grid. No manual copies or patches.

One geography-apply workflow accepts parent-bounded drafts, sources, and a base revision. Incomplete/invalid drafts may be saved for correction but cannot be approved or published. Validate IDs, hierarchy, and source-geometry usability; investigate source-geometry gaps/overlaps. Then validate complete affected-parent coverage against approved parent map cells: every parent cell is assigned exactly once, with no missing, multiply assigned, or outside cells. Polygon checks do not replace this cell-level check. Check conflicts only against affected records and relevant parent boundaries so separate areas proceed concurrently; intermediate levels need no worldwide completion.

At every level, rasterize proposals to actual map cells at the chosen resolution, using IDs for that hierarchy level; previews are not fake location IDs or extra canonical grids. The user reviews **cells, not polygons or vertex lists**: show the approved parent cell boundary and labeled/color-coded children, zoom/pan, selectable sources and rationale, and highlighted issues/island exceptions. Children must partition the approved parent cells exactly once. Parent changes require renewed cell-map review. Only a validated, user-approved proposal version feeds the next level or publication.

After all locations are finalized, run a dedicated river-data and map-review pass before time-dependent attributes. Rivers are selectable line overlays with names/details and practical hit tolerance/minimum visible width; they cross locations without changing cell ownership.

Load and reuse the single compressed grid, with local cell picking by ID and pan/zoom redraws. Use viewer-device WebGL/GPU, not cloud GPU; keep rivers, labels, highlights, and details as separate overlays loaded as needed. Verify desktop/mobile responsiveness in implementation; no speed or file-size guarantee.

One workflow owner carries research through delivery; geography can later parallelize across 10–20+ Luna workers. Serialize shared grid publication only: derive from approved geography, upload a versioned R2 grid, recheck relevant revisions, then transactionally commit matching Neon results and grid reference. Draft saving is separate; failed publication leaves the prior version active, and the app reads matching revisions. No extra publisher, queue, or handoff. GitHub holds code, schemas, docs, and task issues; no research-only PR, and the user merges code/schema/doc PRs.

## Deferred to PR #3

PR #3 covers the 20+ time-dependent attributes, per-location or otherwise, including political affiliation and population, plus definitions, date conventions, and schemas. Agreed starting principles: assign one effective controller per location/date by greatest controlled area when supported (no claims records); cells inherit it. Joint administration uses a documented lead or comparable responsibility/resources; stable IDs are a final model tie-break, not historical fact. Never invent a controller. Population covers all fixed-footprint residents; encourage labeled estimates with recorded basis, show provenance on demand, avoid double-counting, and leave unknown only without a defensible estimate. Zero requires evidence; not-applicable means genuinely inapplicable. Sparse records, no permanent settlement, or present population alone do not prove uninhabited status; consider historical/seasonal habitation.
