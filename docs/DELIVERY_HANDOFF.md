# Prepare a delivery without rebuilding its coordination

`node scripts/prepare-delivery-handoff.mjs PHASE CONFIG DESTINATION [--resume]`
prepares immutable metadata in a managed checkout. The individual preparation phases
never run a scientific operator, accept a source, submit a review, commit, queue
or merge. Publish the real head, obtain
substantive independent review, then use the standard worker integration workflow.
Scientific source/native supervision, rebind, selected-reader and output checks remain authoritative.
Use Node 24 without loaders/preloads. Sparse checkouts need the two literal existing composition
and selected-neighbor helper paths imported by the command; no dataset directory
is required for the code. Missing immutable bodies fail with lazy fetch disabled.

## Execution and memory

SOURCE/NATIVE request templates retain their scientific method, complete immutable
inputs and exact executed-code/runtime identity. New issuance omits resource-only
limits, output reservations and memory forecasts. The ordinary runtime and OS own
memory exhaustion; see [PROCESSING_MEMORY_ADMISSION.md](PROCESSING_MEMORY_ADMISSION.md).
Historical request fields remain literal provenance when reading original evidence,
without enforcing their old memory policy on current execution. Failed or partial
products still cannot establish a successful result.

## Current final-bank authoring

After the support code is accepted, use the existing `finalize` command with
`version: 2`, `selector: {commit, path: "data/ownership-selection.json"}` and
`package_inputs: {commit, path: ".github/package-inputs.json"}` at the actual
accepted selection. The initial conversion forbids new scientific or reference
inputs. It retains N/M, exact E words and fixed compatibility files while making
finished geometry/interval context explicit and issuing a truthful new E identity.
Normal accepted-code joint validation, not the producer, admits the conversion.
The first migration requires a new full package capture.

For later edits, the accepted current-E bank and proposed complete bank are the
map authorities. The same comparison covers additions, owner corrections and
withdrawals of explicit finished native-overlay cells. Original polygon-derived
or N-owned cells retain their existing migration path. It derives the exact changed cells from their decoded words and
requires the same symmetric change in finished native context. Original polygon
coverage/order, owner identity, N/M and unrelated context remain unchanged except
through their existing explicit metadata/migration paths. Withdrawals are reported
as withdrawals, not zero loss; their scientific rationale belongs in substantive
exact-head review. They need no fabricated positive constructor.

Newly positive destinations still require the complete original source/target,
physical-method and assigned/held proof through the existing native constructor.
Version-2 `compose` takes only that proposal's complete rule/binding/constructor/
patch pins and produces `change_evidence`, not a cumulative ledger. The validator
joins its complete assigned scope to actual positive destinations, including owner
transfers. It does not replay old repair hooks to reconstruct the current map.
An unused/restored hook is provenance, not an instruction to append cells.

The existing addition convenience remains: supply the new whole `change_evidence`
pin to version-2 `finalize` to prepare the next complete bank. For an already
prepared correction or withdrawal, instead supply `proposed_selector: {commit,
path: "data/ownership-selection.json"}` alongside the actual accepted `selector`
and `package_inputs`. The finalizer authenticates that complete proposed bank and
uses the same canonical emitter and selector-last writer, without old repair
qualification or a separate rollback workflow. The proposal already carries its
source-evidence hook; do not also supply `change_evidence` or `reference_projection`.
Existing reference-metadata-only preparation remains supported through its complete
`reference_projection` pin. N/source-contract or polygon changes retain their
existing explicit separate path, not an exemption for map-cell edits.

Preparation consumes the complete final words and finished context. Unchanged
compatibility-only members keep their complete accepted index pins and ordinary
Git tree and index identities; only genuine sparse copies may remain absent
instead of being fetched and rewritten. Any materialized compatibility file must
still match its exact accepted bytes. Committed or staged changes, ordinary
deletions, links and nonordinary files refuse before adoption. A member also used by current E is always consumed and authenticated.
This avoids compatibility hydration, not the complete current-E/context read and
whole-stream/footprint hash recomputation. A small key change is not a bounded-row
finalization, and later complete packaging still requires its actual declared
inputs. The ordinary joint consumer separately
qualifies actual positive destinations and exhaustively checks all changed and unchanged cells
and context against the immutable accepted main pinned by the queue. It reads
only applicable positive evidence, never a history of accepted repairs. Pure withdrawals read no positive registry. The next
accepted main is automatically the next baseline; no checkpoint locator, artifact
download, prior-authority ledger or manual promotion is part of this path. No public preparation result is a
scientific capability. Historical evidence remains in Git; `change_evidence` is a
qualification input, not a browser/build product. Version-2 finalization has no
`accepted_checkpoint` option. Keep old evidence as history, not as a prerequisite
for the next repair. Checker upgrades cannot certify their own simultaneous map
changes; that comparison executes the accepted-main checker.

In a managed non-cone sparse checkout, the finalizer derives its complete literal
output path set from the authenticated adoption plan, not a worker-maintained
include list. After full-set preflight it extends the existing sparse selection
and materializes those exact preimages from Git, checking HEAD, ordinary index
identity and worktree bytes before the normal selector-last adoption. Staged or
edited preimages still refuse; exact interrupted resume remains supported.
Unchanged compatibility omissions are not hydrated. Replaced current-bank members
need not be materialized merely for deletion: their exact proven sparse index
entries are removed after adoption, so normal staging cannot retain obsolete bank
URLs. Unrelated index identities and flags remain untouched.

The same staging, full-set preflight, exact interrupted resume and selector-last
adoption below apply. The new expectations point to the complete current bank;
there is no current-ledger expectation. Later final-to-final selected-data changes
can use the existing eligible retained-package route. Unknown/restoration/checkpoint
changes retain the ordinary full plan, and code changes never borrow old output
as a new producer.

## Configurations and explicit commit boundaries

The historical configurations below have `version: 1`. Input pins contain exact `commit`, `path`, ordinary
`mode: "100644"`, `git_blob_oid` (or the existing `blob` spelling), `bytes`, and
whole-file `sha256`. Git confirms the path/mode/OID before the bytes are consumed.
No proposed input is called accepted merely because a hash matches.

1. `requests`: `registry` is the existing accepted administrative-handoff registry.
   Each `groups` item names an `id`, `handoff_id`, pinned SOURCE `template`, exact
   `component_ids` and fresh operator `destination`. Top-level `component_ids`
   declares the complete delivery scope. Groups partition that scope without
   duplication. The whole accepted handoff determines filtered order. Each group
   stays inside its template's actual method/resource scope; the command preserves
   all other scientific, input and runtime fields. It does not invent
   arbitrary batch sizes or classify a new scientific method. Outputs are ordered
   requests and their preparation index. Commit the requests before invoking the
   existing source supervisor separately.
2. `retain`: supply a committed `request` pin, actual local `terminal` receipt path
   and operator `output` directory. The command requires successful exit, no refusal,
   no remaining owned process or termination event, and the actual request binding.
   It verifies every publication product, including declared decoded gzip bytes,
   and joins published facts to that terminal/request. Actual JSONL records must
   match complete issued scope/order/counts; SOURCE targets and source-case bindings
   join the pinned whole handoff. Native retention requires the fixed complete asset
   roster, an independent effective-target join through the immutable SOURCE
   request and whole handoff, and actual inventory/ledger/patch/envelope agreement. For rebind output, also supply
   `custody` local paths for `code_source`, `issued_plan`, `stderr`, and `stdout`;
   raw code-source, issued-plan and stdout are joined to the immutable issued
   execution contract before provisional retention. These bodies remain provisional
   until the subsequent committed operating phase verifies full execution custody.
   Failed or partial runs remain
   failed. Originals are never overwritten. Commit retained bodies before the next
   phase; there are no fabricated future commit pins.
3. `native-requests`: each group has `id`, pinned native `template`, fresh
   `destination`, and `source` pins named `request`, `publication`, `facts`,
   `inventory`, and `operating`. Those are actual committed qualified SOURCE
   results. Native scope/baseline must agree with the source. Only these explicit
   source slots, source execution/runtime identity and destination are replaced;
   other template fields remain literal. Commit and use the existing native
   supervisor separately, then retain genuine results with the same phase.
4. `compose` and `finalize` use only the version-2 final-bank configurations
   documented above. The old cumulative `package` phase, sidecar composer,
   checkpoint option and version-1 finalizer are retired. Source/native request,
   retention and immutable evidence remain distinct from current map authoring.

### Derive the canonical source-evidence baseline

`node scripts/prepare-delivery-handoff.mjs source-evidence CONFIG DESTINATION [--resume]`
replaces manual assembly of the accepted baseline block. The local configuration
contains `version: 1`, `selector: {commit, path}`, an explicit `source_evidence`
scientific payload. The payload uses the existing `source-target-native-evidence-v1` format; source/physical pins,
targets, geometry, exclusions and other scientific claims remain the operator's
explicit reviewed inputs.

A target's optional `coverage_rows` binds the land/water class of the complete
requested native patch for its owner (`pixelIndex`), not that source member's
geometric coverage. When using `coverage_rows` for same-owner siblings, one
reviewed complete owner binding on any target suffices; the others may omit it.
If supplied on more than one sibling, the complete bindings must be identical.
Each binding uses sorted, nonoverlapping half-open `[start, end, class]` runs and
must cover exactly that owner's requested cells; partial per-member rows,
conflicting class bindings and extra cells are refused. Do not union partial
rows, treat request-mask membership alone as physical class evidence, or omit a
required class binding to bypass admission. The preparation command preserves
this scientific input, and the native consumer still checks actual source/physical
support and every retained sibling veto.

The entry authenticates the selected sidecar, base manifest and runtime envelope,
then fills only `native_contract`, `native_latitudes`, `owner_roster` and
`base_reference`. Supplied versions of those fields must match exactly. The
normative contract is copied literally from the base manifest; Git mode/blob
metadata belongs only to separate custody pins. Raw and decoded latitude/owner
identities are verified before output. No template commit or scientific execution
is needed for this mechanical assembly.

For reviewed whole-original negative sources that have no native owner, opt in
with a top-level `territorial_exclusion_families` array of exact original catalogue
family keys. This explicit scope must be reviewed for the package; the helper does
not infer foreign status or legal applicability from names, prefixes, or absent
owners. It supports original v1/v2 source families, not revised/provider adoptions.

The same `source-evidence` command authenticates the complete catalogue products,
every ordered encoded/decoded part, original feature identities and complete
physical source/selected-target joins. It appends unchanged whole original
geometries whose complete bounds touch/intersect each consumed source member.
Multipart components are retained together; seam-spanning bounds widen
conservatively. Existing exclusions and their ordinals, positive families,
coverage rows and requested native denominators remain unchanged. Malformed
originals fail even if their bounds would otherwise be disjoint.

To avoid repeating large whole polygons, also set the top-level
`compact_territorial_exclusions: true`. Each uniquely matching original operand
becomes `{source_id, feature_ordinal, negative_ordinal, geometry_sha256}` at the
same target position. The output's `territorial_exclusion_sources` contains each
complete negative family as `{source_id, parts}` using the existing immutable
encoded/decoded source pins. All original features remain authenticated, including
unused/disjoint features. Unmatched or ambiguous manual geometries stay inline.
Intentional repeated geometries retain distinct positions; copied or moved
reference records fail their exact ordinal binding. Incomplete families, unknown
source IDs, malformed references and ordinal/hash mismatches fail closed.

The native reader expands these references to their unchanged complete original
geometries before the existing applicability and veto checks. It does not derive
positive ownership or a contextual exception. Legacy inline inputs remain valid;
omitting the flag or setting it to `false` preserves literal inline output. New
custody hashes and evidence-derived component IDs necessarily change with the
encoding, while native requests, decisions, whole operands and source receipts do
not. This option requires the explicit reviewed negative family list.

complete family pins, original feature ordinals/hashes, target exclusion ordinals

conservative disagreement handoff, not a sovereignty decision, applicability
exception, positive source/owner mapping or native acceptance. Run the unchanged
full requested native diagnostic/qualification; do not delete held cells from the
original request. Without the optional scope, ordinary preparation is unchanged.

Commit the emitted ordinary `source-evidence.json` once, then pass its immutable
locator to the existing `native-authority` command. This step does not qualify the
scientific claims or replace their review. Choosing a different same-body custody
commit can change evidence bytes and authority IDs: use normal qualification of

### Reuse supported diagnostic inputs

`node scripts/prepare-delivery-handoff.mjs supported-inputs CONFIG DESTINATION [--resume]`
replaces a package-local post-diagnostic writer. Use version 1 and a `diagnostic`
commit/path locator. The helper reads that retained result's exact original source
and patch pins, checks its requested/supported/held decision partition, and emits
`source-evidence.json`, `native-patch.json`, `held-original.json` and
`original-scope-partition.json` through the existing exclusive publisher.

When earlier source review held additional original cells, also supply
`original_patch` and `prior_holds` commit/path locators. The original patch uses
the existing `{rows: [{y, runs: [[start, end, owner]]}]}` representation. Prior
holds use the existing held-output representation, with a fourth non-assignment
reason on each run. Their complete retained assessment document stays pinned in
the accounting; no copied proof boolean is accepted. Prior holds may overlap
either native partition, but must belong to the original scope. All original
cells must be accounted for by the diagnostic or prior holds. Native reasons
remain on already-native-held cells; the prior pin preserves concurrent reasons.

coverage rows are intersected with final supported keys, preserving each original
land/water class. Every member atom of a surviving owner remains, together with
all other target fields, whole source/physical descriptors and negative operands.
