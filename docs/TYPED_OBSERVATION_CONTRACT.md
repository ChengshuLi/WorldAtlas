# Shared typed observation contract, version 1

This is the first bounded part of issue #529. It defines an additive, pure contract and explicit module registration seam. It does not enable hosted imports, add tables, advertise a production capability, implement domain map modes or close #529. The existing eight attributes, identities, source archives, immutable migrations and v1/v2 storage exports retain their contracts.

`src/observation-registry.js` distinguishes a polity's exclusive government class from location measures and separately linked feature identities. Stable type IDs reuse existing graph kinds where applicable. Vocabulary definitions are structural definitions, not factual assignments. The initial registry contains no government classifications, language assignments, ports, diseases or geographic feature data.

`src/typed-observations.js` is the common normalization/resolution seam for subsequent hosted and prepared/static adapters. A version-one observation contains `id`, `subject_id`, `subject_kind`, `field_id`, explicit `value`, supported `valid_from`/`valid_to`, `source_id`, `method`, `status`, `is_example` and JSON `metadata`. Normalization needs the existing source and entity catalogs; unknown IDs, wrong kinds, unsupported source intervals and subject/value lifetime overflow fail closed. Caller-owned source and metadata objects are not rewritten. A resolved record retains its full normalized evidence. Original evidence stored before this extension must never be retroactively normalized or relabeled.

Intervals are sparse, inclusive at the start and exclusive at the end, 3000 BC through 2026 AD, without year zero; 2027 is only the final end sentinel. Nothing carries a value beyond its supported interval. A missing observation returns unknown through `typedObservationAt`; it does not prove absence. Unknown/unresolved/disputed/no-majority require null. Supported numeric zero and boolean false remain known. Example entities, values or sources cannot enter unlabeled factual claims; examples require explicit opt-in at resolution. Reference sources require reference evidence and remain reference, not historical facts. A modern reference's support cannot be extended into antiquity.

Resolution shares the existing location evidence precedence through `src/evidence-priority.js`: direct, derived, reference, estimate, then opted-in examples. Explicit unknown evidence participates at its stated priority. Equal priorities use the stable claim ID, independent of ingestion order or locale. Typed callers cannot inject custom priorities. Withdrawn observation IDs are excluded without deleting or changing the original evidence. Storage-backed retirement and source-supported conflict enforcement remain later adapter work; this pure helper does not authenticate retirement IDs or authorize imports.

Priority follows the method, not the status. A directly quoted source estimate retains `status: "estimate"` while sharing direct-method priority, as in the existing resolver. A reconstruction intended to use estimate-method priority must explicitly use `method: "estimate"`. Labels and uncertainty are never erased by choosing a claim.

Numeric metadata uses `measurement` with a registered `unit`, explicit `definition` and supported half-open `period`. GDP units distinguish total output from per-person output and constant GDP PPP from consumption PPP. PPP observations additionally declare `price_basis: "constant"`, `ppp_scope`, `benchmark_year`, `series_id` and `comparability_group`. Canonical median purchasing power requires a documented `equivalence_scale` and `weighting_basis: "person"`; it is not mean income. Adult literacy uses `percent` (0–100) and `cohort: "age-15-plus"`. Disease-death measurements explicitly declare `period_basis: "annual"`; a cumulative total is incompatible. This declaration does not establish actual source support for annual allocation or permit spreading cumulative deaths uniformly.

JSON metadata retains original values/units, benchmark and PPP scope, household scale, cohort, observation period, source-byte/hash and release references, coverage, precision, assumptions and uncertainty. Numeric uncertainty bounds must contain the observed value and respect metric bounds. `derivation_input_ids` are retained, unique and cannot reference the claim itself; derived evidence requires inputs. Validating a full dependency DAG, compatible GDP identities, uncertainty propagation, mortality deduplication and supported conversions belongs to the domain children. Merely supplying metadata does not validate those algorithms or historical claims.

Typed relationships use existing source/entity endpoints and dated evidence with a registered `relationship_type`; the pure contract checks endpoint kinds and lifetimes. An outbreak/location link does not compute deaths; a port/location link does not establish active operation or maritime capability. River/lake/shoreline contact definitions preserve true/false/unknown and separate marine shores from inland lakes. Missing coverage does not establish false. Feature geometry, full contact methods and approval gates remain separate work.

## Controlled module registration

Domain workers add one owned declarative module and tests. Its module ID is unique lowercase text; extension IDs begin with `module-id.`. Supply version 1 and optional `types`, `metrics`, `fields`, `relationships` arrays, then pass an explicit module list to `createObservationRegistry`. Each entry has a stable `id` and `definition`. Fields declare registered `subject_kinds`, one of `number`, `boolean`, `identity`, `identity-list`, and either `metric_id` or `value_kind` as applicable. Numeric metrics declare `unit` and optional numeric bounds; links declare registered `source_kinds`/`target_kinds`. Duplicate IDs, invalid references, executable functions and replacement of the core namespace are rejected. The resulting registry is deeply frozen.

There is no global mutation, filesystem/plugin discovery or dependency on registration order for resolution. The coordinator later assembles one reviewed module list; workers do not each rewrite shared registrars. Existing core definitions are reused. New definition versions or changed semantics require explicit compatibility review; this version-one loader does not silently accept version two. Domain children wait for #529 completion and the issue coordinator's explicit readiness, even after a partial contract PR merges.

JSON validation inspects data descriptors before reading or serializing them. Hooks, accessors, hidden/symbol properties, custom prototypes, sparse/decorated arrays, cycles and depth beyond 64 are rejected without running hooks/getters. Ordinary parsed JSON retains its values and metadata; a serialization callback cannot substitute a different module identity or evidence object.

## Remaining compatibility and integration work

Before #529 can close, subsequent fresh PRs must provide reviewed forward storage/import/read support on supported adapters, compatible optional API capabilities, old consumer/export preservation, actual server/static/prepared/snapshot parity fixtures and the final module handover. Existing deployed migrations are immutable. A new table cannot silently disappear from full raw backup: inventory checks must remain strict, and a reviewed versioned export/restore extension is necessary if tables are added. No provider DDL, baseline transfer or factual import occurs on a normal merge.

The first-part tests exercise JSON transport through the pure shared seam and unchanged legacy resolution, not production adapter parity or a browser/mobile certificate. No live endpoint advertises typed observations yet. Subsequent adapters must preserve old payloads and hashes byte-for-byte, gate factual imports by current regional approval, and explicitly check source catalog, lifetimes, immutable conflicts, supported intervals, retirement and release pins. Structural empty datasets are valid. Publication, rollback and owner maintenance require the designated publisher protocol on issue #39; source checks are not historical or geographic approval.
