# Cloudflare hosting with existing Neon

For a public website, explicitly build with `ATLAS_PUBLIC_READ_ONLY=1`. This permits anonymous reads and forces read-only behavior even if `ATLAS_READ_ONLY=0` is accidentally configured. Private JWT protection remains the default for every other value. Deploy the reviewed public package before removing the corresponding Cloudflare Access application; otherwise the edge login still applies. Preserve the previous private configuration for rollback.

Before accepting either access mode, compare the static `atlas-geography.json` reference release with the live temporal snapshot's release ID, hierarchy hash and footprint hash. Exercise the combined historical loader, including inline temporal pages. HTTP 200 responses alone do not establish matching releases; staged static release6 and published Neon release5 are incompatible. Serve the verified published release's matching assets or complete its separately authorized publication; never weaken the loader's pin checks.

The Cloudflare build deploys the hosted atlas API and fixed map assets to the user's account. It is the ongoing publication target in [PUBLICATION_HANDOFF.md](PUBLICATION_HANDOFF.md), whose planner reads real Cloudflare and retained Site/native histories together. Neon remains the existing PostgreSQL project, runtime role and compact schema. No database provisioning, migrations or content imports run during publication. Serving rollback uses a retained verified Cloudflare version with matching current data; old Sites source/storage remains recovery history and is not automatically a compatible current-release serving fallback.

## Build and optional private access

Use Node24, `npm ci`, and the pinned Python preparation dependencies in `requirements.txt`. The intended public website uses `ATLAS_PUBLIC_READ_ONLY=1 npm run build:cloudflare` from its classified immutable compatible primary commit. Keep public writes disabled and verify anonymous root/assets/API/media access. Do not recreate an Access login gate for the public host. Code collaborators use GitHub; public browsing does not grant publication or database-write access.

For a separately authorized private deployment only, configure an Access application/explicit email allowlist, set `ATLAS_ACCESS_TEAM_DOMAIN` and exact `ATLAS_ACCESS_AUD`, and use the default private build. This does not change the preserved old Site's audience. Both builds produce `dist/cloudflare/wrangler.json`, the Worker entry and `dist/client/` assets. The standard prepared-asset pipeline runs without D1 migration packaging or Sites archive transport. Wrangler dry-run/deployment must verify actual account limits before release.

Private mode verifies JWT signatures/issuer/audience/expiry and fails closed on invalid configuration. Explicit public mode instead forces reads only before delegating any request, including when another write flag is wrong. `assets.run_worker_first:true` is essential for either boundary. Preview URLs remain disabled; new domains require the same explicitly selected mode and verification.

## Secrets and deployment

Use a scoped Cloudflare API token, restricted to the intended account, with Workers Scripts Edit, Workers R2 Storage Edit, Account Settings Read and Access Apps and Policies Edit. Initial organization/identity-provider setup also needs Access Organizations, Identity Providers, and Groups Edit. Keep the token outside Git and pass it through `CLOUDFLARE_API_TOKEN` in the deployment process environment, with `CLOUDFLARE_ACCOUNT_ID`. Never put credentials in command arguments or logs.

Use the existing private `worldatlas-archives` bucket bound as `BUCKET`; keep direct public bucket URLs disabled. Register and start the serialized provider-specific operation **before** deployment, then deploy the reviewed generated package with `npx wrangler deploy --config dist/cloudflare/wrangler.json`. Preserve the existing restricted runtime-role `DATABASE_URL` secret. Initial installation, if separately needed, uses a hidden prompt/stdin; do not replace it with an owner URI or rotate it during ordinary publication. Keep secrets out of configuration/source/evidence. Verify actual provider version, all exact package/release/lookup/backend pins and served behavior before settlement.

The build selects `ATLAS_CONTENT_BACKEND=postgres` and `ATLAS_READ_ONLY=1`. Public mode rejects mutations regardless of that second flag. Ordinary publishing does not enable writes; a separately authorized import/maintenance mechanism has its own role/transaction gates. A read-only app flag is not a database-wide SQL maintenance lock.

## Archives and cutover

Sites-managed R2 belongs to the existing Site's storage context. It is not the new account's bucket. Retrieve an actual complete inventory/export using the owning Site account or a preserved verified export. Copy original object bytes under the same keys, retaining content types and checksums. Compare every copied object's byte length and SHA-256 with its authoritative inventory, and resolve any collision before proceeding. Tracked reference archives alone do not prove completeness of later uploads. Do not silently regenerate archives, rewrite database object keys or declare migration complete from an empty bucket.

The current database recovery/compaction publisher operations own their production windows. Coordinate with their original issues and the durable publication registry before any shared-data operation or write restoration. Migration preparation does not supersede their read-only state or authorize another publisher.

Before public acceptance, pin reviewed code, current published release, prepared assets/lookup and compact database state. Verify anonymous reads work, all public mutation methods are rejected, map/date/search/content behavior matches those pins, and media checksums agree. Private deployments additionally verify authorized/unauthorized authentication behavior. A Worker receipt alone does not establish data parity or current-main delivery. Imports/idempotency use independently authorized isolated tests or their designated maintenance protocol.

Preserve old Site/storage, originals, backups and receipts after migration. Retiring obsolete serving/publishing activity is separately tracked and requires verified current recovery; it never authorizes deleting storage. Rollback changes serving to an explicitly verified compatible retained version without restoring/overwriting Neon. Ongoing publication preserves scoped credentials, independent review/CI, the global operation registry, exact source/data pins and manual settlement; no automatic database migrations or duplicate schedules.
