# Direct candidate physical stage

This isolated prototype produces **physical land versus water**, not continent labels or a released map. No historical/V2 raster or label data is needed to build it. A pinned OSM-style land polygon snapshot is rasterized to land; a complete pinned Overture GeoParquet shard set is rasterized as selected water, unioned, and subtracted from land. The resulting binary dry mask is encoded as physical runs. Reference comparisons are optional validation only.

Grid for this project: width 131072, height 54614, west -180°, north 90°, step 360/131072°, rows north-to-south, EPSG:4326. Physical rows are little-endian uint32 offsets, one per row plus terminal offset, into little-endian `(exclusive_end_column, code)` uint32 pairs. Every row covers the full width. Physical code 17 means dry land, 1 means water. Consumers must use the streams' recorded SHA-256 hashes. Continent assignment and component generation are separate stages.

## Orchestrated run

`build_physical.py PIPELINE_CONFIG NEW_OUTPUT_DIRECTORY` wires the four stages below from hash-pinned input configs and the complete raw shard manifest. Copy `pipeline-config.example.json` and replace all placeholders. References are optional; the same stage isolation, hash checks and free-space reserve apply. `max_parallel_shards` sets a bounded worker count from 1 to 32 (default 1); choose it for the machine’s memory, I/O and disk headroom. Each worker checks the reserve, but concurrent writes can cross it between checks, so leave additional headroom. The pipeline report records the generated hashes. Run `python -m unittest -v test_build_physical.py` for the small raw-source end-to-end test.

## Reproducible steps

Requires Python 3, NumPy, GDAL/OGR Python bindings with GEOS, the GeoTIFF, Memory vector and raster drivers, and PyArrow Parquet support. The proven setup is Python 3.13.5, NumPy, GDAL 3.10.3, GEOS 3.13.1 and PyArrow 26.0.1. Use the same versions when byte-for-byte reproducibility matters. Disk requirements are substantial; each stage stops if the configured free-space reserve is crossed. Output directories must be new, outside all input directories, and must not contain inputs. A failure can leave partial output without a success report; preserve it until disposal is authorized.

1. Copy `land-config.example.json`, specify each land dataset and **all** sidecars as explicit path/SHA-256 pins, and explain provenance/selection in `selection_notes`. The tested candidate used the November 3, 2026 OSM mirror, not the missing historical OSM snapshot. `where: null` deliberately selects all features. Run `python rasterize_land.py CONFIG NEW_OUTPUT_DIRECTORY`. The builder verifies hashes before and after, requires EPSG:4326, valid non-empty polygon geometries, and does not repair or reproject. It writes `land.tif` and report. GDAL polygon defaults apply with ALL_TOUCHED off. No claim is made that boundary/tie or antimeridian behavior matches historical code.
2. Copy `overture/config.example.json` and pin a reviewed water policy and grid. For each **raw** Overture GeoParquet shard, run `python overture/rasterize_water_shard.py SOURCE SOURCE_SHA256 CONFIG NEW_OUTPUT_DIRECTORY`. Each report binds raw digest, policy, grid and output digest; unclassified or invalid selected geometry marks it incomplete. Do not union an incomplete shard. This implementation chooses OSM feature/geometry provenance and excludes ocean, physical labels and ocean/sea classes; the historical predicate is unknown.
3. Copy `overture/aggregate-config.example.json`. Supply the hash-pinned complete raw-source manifest (`file_count` and `files` entries with `sha256`), each shard TIFF and its hash-pinned report. The code checks the manifest's distinct source hashes are covered exactly once, all shard outputs match their reports, grid and policy agree, and reports are complete. Run `python overture/aggregate_compare.py CONFIG NEW_OUTPUT_DIRECTORY`. It writes `water-union.tif` and report. The comparison reference is optional; adding `reference` with `path` and `sha256` records full-cell differences but does not alter the union. Raw source files are individually checked during step 2; retain the source manifest, reports, policy and source files for audit.
4. Copy `compose-config.example.json`; pin the two resulting mask TIFFs and describe provenance. Run `python compose_physical.py CONFIG NEW_OUTPUT_DIRECTORY`. It writes `physical-dry.tif`, `rows.u32le`, `runs.u32le`, and a report including grid, input pins, counts and output hashes. Optional validation can add **both** `reference_mask` and `reference_streams` (with `rows` and `runs`, each path and sha256); the builder checks consistency and emits every mismatch. Comparison does not determine or change the candidate. No V2 continent labels enter this stage.

`build.py` supplies strict shared pin, geometry, and optional reference utilities; it is not the entry point for the recommended flow. Mask outputs, reports, inputs and configs are all checked for change; the configuration itself is retained with outputs. Reports and comparisons do not prove geographic correctness or historical provenance. Explicit review of source selection and any differences remains necessary.

## Tests

`python -m unittest -v test_rasterize_land.py test_compose_physical.py`, then from `overture/`: `python -m unittest -v test_aggregate_compare.py test_rasterize_water_shard.py`

Synthetic tests cover polygon rasterization, source/digest checks, geometry and output isolation, stripe/batch behavior, report/manifest lineage, incomplete or inconsistent water shards, optional reference-free and reference-checked composition, run encoding and nonbinary masks. They do not establish real-world source correctness. Keep memory/disk limits appropriate for the full grid.


## Shard concurrency baseline

On 2026-11-04, two runs processed the first 20,000 rows from each of two real Overture shards on the full grid. Serial elapsed times were 2.526 and 3.641 seconds; two workers took 1.315 and 1.561 seconds. Sampled combined RSS was about 159–160 MiB serial and 305–309 MiB with two workers. Each corresponding mask matched byte-for-byte. The subsets came from Overture shard 22 and shard 13 and had SHA-256 values `90a10a4f5bc9042c56c2ea044a271b25c4bc6a57ca03c074f05d00cf49f05ffd` and `492d2d58ab4efb1cfafccde3dd015a4c04ef81119b8fdd4edf2a247cb8ffed10`. The run used Python 3.13.5, PyArrow 26.0.1 and GDAL 3.10.3 on a container reporting nine CPUs. Run order was reversed for the repeat, but cache and external load were uncontrolled. These small subsets are not a complete release or a full-pipeline throughput guarantee; use explicit worker limits and benchmark the real workload.
