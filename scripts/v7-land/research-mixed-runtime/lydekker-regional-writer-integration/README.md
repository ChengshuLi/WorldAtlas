# Mixed-writer integration preparation
This is an experimental preservation checkpoint. It does not activate the regional rule in the driver. An independent reviewer found no new blocker in the bounded bridge and source-resolver tests; full driver activation has not been reviewed.


This local research helper maps a freshly computed, authenticated regional result to the existing whole-component mixed-writer claim shape. It preserves selected source affiliations, holds explicitly pending roots, refuses stale snapshot/component/line pins and conflicting or reviewed regional proposals, and keeps a separate audit trace for the regional rule. It does not read a saved historical comparison or write a grid.

The existing writer was exercised with a tiny synthetic row, not a world-map build. Before production use, the caller still needs to export and authenticate the selected Neon regional record, rerun the source/group/line and satellite resolvers from pinned physical inputs, supply the current known pending roots and protected witnesses, and bind the complete regional policy and code into the writer request and report. The mixed driver currently requires its reported affiliation-statistics keys to exactly equal the selected List 1 affiliation IDs. Integrating this additional rule therefore also requires separating the regional rule's statistics from that existing equality check. This helper is not connected to the mixed-land driver and no map was built.

Every independent region-claim channel must be wrapped with `protected_region_rows`; otherwise a pending, protected or reviewed root can still be changed through that separate overlay path. The bridge unions pending roots explicitly reported by the regional run with caller-supplied pending roots. Withholding new claims does not make cells unassigned: the current writer retains their baseline codes. The per-root trace carries line, satellite or group evidence separately from the synthetic writer affiliation; production wiring must bind that trace to the same-run policy, source and physical lineage. The helper cannot itself distinguish a freshly computed result from a reloaded preview: same-run authentication remains a caller obligation.

`source_groups.py` is an experimental source resolver for the selected policy's eight OSM features. It checks exact source and physical-input bytes, re-extracts pinned geometries, validates each named witness against its polygon and current component, and emits only complete-component windows plus independently named anchors. The supplied `run_source_groups.py` is a bounded workspace-specific diagnostic, not a production invocation or a substitute for a supervised process and source-catalog authentication. Its small synthetic tests are not an independent geographic review.

The bounded workspace diagnostic re-extracted all eight pinned features from the authenticated source archive, validated their named witnesses and complete-component coverage, and found six independent named anchors. Its fresh root sets matched the prior bounded source diagnostic. No map was built. This validation does not prove all group membership or a complete pending inventory.

### Experimental no-build orchestrator

`live_driver.py` composes the existing regional research pass, source feature and extent resolution, direct-satellite review and the writer-shaped claims bridge. Its caller must authenticate the selected policy, current snapshot and all resolver reports, physical lineage, pending inventory and runtime dependencies; a hash supplied by an unauthenticated caller is not an attestation. It does not connect itself to the map driver, fetch Neon, or write a map. `test_live_driver.py` exercises composition and holds with fakes; it is not a real-source acceptance test. A caller that uses the bridge must wrap every region-claim callback with `protected_region_rows` and report synthetic regional statistics separately. Withheld claims leave the baseline code in the existing writer, so they are not proof of resolution. Source-group associations and satellite thresholds remain research conventions. Full deployment requires a same-run authenticated replay, complete pending inventory, actual-writer tests and independently reviewed driver wiring.

`run_live_driver_diagnostic.py` is a workspace-specific bounded exercise of that orchestration, not a production driver. With the pinned source files and current physical streams it produced 5,218 regional proposals and 1,268 reviews, with no target-code changes versus the earlier bounded preview. This used archived reconciled selected-resolver reports and an empty pending list despite incomplete pending-inventory evidence. It therefore neither proves a fresh source replay nor authorizes a production map. The accompanying overlay integration test checks that the orchestration's writer bridge blocks pending and protected roots in the independent region channel while retaining their baseline codes.

### Experimental driver connection

`apply_selected_mixed_regional.py` is an opt-in research overlay of the pinned mixed driver; it is intended to be installed as that runtime's `apply_selected_mixed.py` only in an isolated, supervised candidate. It invokes `driver_hook.py` with the selected source-resolver reports produced in the same driver execution, checks the caller's snapshot hash, passes regional component claims into the writer, wraps the independent region callback for protected/reviewed roots, keeps selected affiliation statistics distinct from synthetic regional statistics, and retains regional evidence in the research report. Code and regional inputs are hash-pinned and rechecked before reporting. The driver remains unpublished research and the separate process-group and disk monitor remains required.

This is a preservation checkpoint, not an activation approval. `driver_hook.py` requires a pinned policy, line, pending inventory and runtime dependencies. An incomplete inventory may be used only with `profiling_standin: true`; this flag records a limitation and does not make the results final. The caller remains responsible for authenticating that policy and inventory, establishing lineage and source rights, verifying the actual-driver integration, and not publishing a profiling result as accepted geography. The original driver's strict requirement that each selected affiliation apply at least one cell remains in force; pending or conflict holds may make it fail closed rather than complete an output. The candidate driver has not yet completed a real-source full-driver test.
