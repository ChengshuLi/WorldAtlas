# V7 Neon-backed presentation research overlay

This code prepares an isolated overlay of a byte-pinned historical V7 UI. It replaces the release-specific List 1 renderer import with the generic data-driven renderer and obtains presentation records from a same-origin service. It does not deploy the UI, publish data, create credentials, or modify the private comparison Site. The original UI stays intact.

`presentation-service.mjs` is a pure handler prototype, not a provisioned service. `neon-release-lookup.mjs` supplies a parameterized, size-bounded query adapter around a host-supplied authenticated database query function; it creates no connection. The host must use a read-only Neon identity and verify the exact release and existing R2 source bytes through the reviewed presentation-export verifier. The query bounds manifest and record text before the driver loads them; the handler separately bounds serialized output. It returns the canonical JSON envelope `{schema, manifest, records}` with schema `worldatlas-presentation-transport-v1`. The manifest and records come from the verified Neon release; do not check release data into GitHub or write a generated presentation JSON object to R2. Deployment must provide the expected manifest SHA-256 and release ID through independently trusted release configuration. Taking those values from the same untrusted response would not establish source authenticity. Use TLS, explicit authorization, rate limits and an operational security review before exposing a service; no credentials are created by this prototype.

`prepare_ui_overlay.py` requires caller-supplied hashes for every input, validates bytes read from the same descriptor, applies only exact, unique patch anchors, and writes to an empty local output directory. Treat output paths and the executing Python environment as trusted. The browser client rejects a missing or cross-origin endpoint, malformed/noncanonical or oversized transport, a manifest differing from the independently supplied digest or release ID, and mismatched records. It verifies proposal, water-presentation and reference-index bytes before using each one, and the original UI's full reference-index equality check remains in place. A verified manifest is not a signature and does not protect against a compromised release configuration, trusted service, executing code, or a privileged database owner.

The portable client unit test uses fictional data. The Node integration test takes an independently authenticated Neon export and historical source files as runtime arguments, reruns the pinned verifier, and exercises the original list-rendering functions against both indexes in a DOM-shaped model. It checks 108 land leaves, exact full-index and model output, interactions, startup order and negative paths. This is not a real browser, map renderer, service authentication test or a complete UI startup. `test_browser_integration.cjs` exercises the same historical list functions and transport in Chromium at desktop and mobile widths when an existing browser and Playwright are available. The current client passed the historical fixture at 1280 and 390 pixels with exact DOM parity, 108 island members, hover/click callbacks, and eight rejected negative cases at each width. The never-settling cancellation cases are synthetic-only. Its non-Linux handoff mode rechecks bytes but does not itself authenticate the Neon connector or reproduce the Linux sealed verifier. Neither test proves full live-site parity.

For the real-export Node test and Linux browser test, set `V7_PROJECT_ID`, `V7_BRANCH_ID` and `V7_DATABASE` to the independently authenticated Neon origin; these are assertions, not credentials. Both test scripts take the project root, generated UI directory, local manifest, local exported snapshot, source-input directory, manifest digest, snapshot digest, release ID and code revision as positional arguments. `V7_SOURCE_ROOT` and `V7_PROTO_ROOT` can override the handoff's default source and prototype directories. Do not commit the real fixture or generated UI to the repository.

The separate `test_startup_browser.cjs` uses a locally preverified handoff and exact historical dependencies. Chrome 156 passed at 1280 and 390 pixels: the actual old and candidate list startup, accounting/legend checks and list DOM matched with 108 members, and tampered records and altered proposal were rejected before rendering. The final grid load and map rendering were deliberately short-circuited; the lookup used an in-memory verified export rather than live Neon. This does not validate the actual deployed site or a rollback.

## Safe release and rollback plan

1. Preserve and independently verify the current historical UI's exact assets, source data, code, immutable URLs and release configuration. Establish which URL is actually served; a stored artifact alone is not proof of the current live deployment.
2. On an isolated staging origin, provision and security-review the read-only service, inject the independently authenticated release pin, and test full browser startup, maps, list text, search, pointer/keyboard interactions, mobile layout, error paths and cache/version transitions against the historical UI. Confirm the staged endpoint handles database failure without silently falling back to stale records. The current prototype and fixture are not sufficient to authorize promotion.
3. Promote only after explicit deployment authorization and verified full parity. Keep the previous UI bundle and its dependencies at their original immutable versioned paths. Use versioned entry points so old and new scripts or metadata cannot be mixed by caches.
4. If verification fails or the service becomes unhealthy, restore the prior versioned entry point and old static bundle as a single rollback, without deleting either set of assets or changing the Neon release record. Validate rollback on staging first and check actual browser rendering after any production switch. This rollback has not yet been exercised.
