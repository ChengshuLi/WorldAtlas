# Source-point whole-component resolver (research prototype)

This standalone, fail-closed diagnostic resolves point features from pinned source files to whole components of a new physical mask. It reads no V7 labels, old mismatch spans, preassigned component IDs, or geographic decisions from code. Each island identity, point, target entity, source version and selection status must come from the input decision snapshot. The result is a research claim trace, not a land map, accepted Neon export, List 1 build report, or release.

The portable part is the source feature identity and its point geometry, not the resolved component ID. Re-resolve for each newly generated physical mask. A source point identifies one physical component only; it does not select nearby islands. A point or a document hash alone does not prove that the component is the claimed island, that the selected target is correct, or that it matches V7. Reviewers must establish those facts independently, including whether raster connectivity incorrectly merges or splits physical islands, and validate the new final comparison for both missing and extra changes.

## Contract

The input request `point-component-request-v1` specifies `grid`, pinned `snapshot`, `component_manifest`, `component_source`, `physical_rows`, `physical_runs`, `component_rows`, `component_runs`, `source_files`, and `resolver_sha256`. Every file pin is `{path, sha256}` with a lowercase SHA-256. `source_files` also contains `source_id` and `version`; it must exactly match the source identities and digests in the snapshot. The grid has positive integer `width`, `height`, decimal `west`, `north`, `step`, north-to-south rows, and WGS84 longitude/latitude. The global longitude extent must be exactly 360 degrees from -180, the northern edge must be +90, and the latitude extent may not exceed 180 degrees.

The draft-only `point-component-decision-snapshot-v1` identifies its `source` as `neon-export`, status `draft`, and a nonempty `revision`, plus arrays `sources`, `target_entities`, and `decisions`. This schema is proposed and is **not yet implemented in the Neon exporter**. Hashing a file or writing `neon-export` into it does not authenticate its origin. Every source has unique `(source_id, version)`, SHA-256, byte size, R2 bucket/key, URI, title, provider, attribution and license metadata. Only original raw source assets with no derivation parents are supported; no derived coordinate GeoJSON is uploaded or accepted. Every target entity has a unique integer `id`, a name and physical class `land`.

Each decision supplies a unique `affiliation_id`, method `source_point_component_v1` or `source_point_named_region_component_v1`, `execution_status: selected_for_research`, integer target `entity_id`, `island_identity`, `point_name`, point and independent identity source IDs/versions, `source_feature_id`, `id_property`, and canonical `geometry_sha256`. The point source must itself be a provider-original raw GeoJSON FeatureCollection with exactly one feature whose `id_property` string matches the source feature ID, whose `properties.name` equals `point_name`, and whose geometry is a 2D Point. Geometry SHA-256 is over the UTF-8 JSON geometry with sorted keys, compact separators and non-ASCII preserved. For `source_point_component_v1`, the separate identity source is a pinned document and a hash does not validate its interpretation. The distinct `source_point_named_region_component_v1` instead references an identity-polygon decision feature and its raw source via `affiliation_feature_refs` role `identity_polygon`; its exact selector adds `identity_id_property`, `identity_name_property`, `identity_class_property`, and `identity_class_value`. The pinned `named_identity_sha256` implementation and separately pinned `identity_watch_sha256` use an isolated RSS/host-memory-watchdog process and OGR/GEOS to require valid named polygon identity and strict point containment. This only corroborates the point; generalized identity polygons never define or select the physical island boundary.

For a `worldatlas-geography-decision-draft-evidence-v1` combined export, the pinned `adapter_sha256` is also required. The adapter makes an internal view without claiming it is another Neon export; it requires a revision-bound `identity_evidence` source reference and exactly the selector keys `island_identity`, `point_name`, and `id_property`. Point and identity sources are independently catalog-pinned. The actual exporter/schema extension remains unexecuted, and code never writes Neon or R2. Derived provider responses needing extraction are currently unsupported; a future reviewed runner must read the raw provider response and extract locally.

Component lineage can be either the existing `single-generation-component-manifest-v1` or a pinned completed WGS84 `simple-v2-land-report-v1`. The latter must bind the exact physical/component streams, original builder source and binary, physical report, prior independent spherical report and checkpoint header, including the original component hashes. The WGS84 run did not independently regenerate topology; this route does not claim that it did. The original same-generation manifest includes grid and exact stream pins, component-builder source and binary hashes, builder/compiler evidence and a candidate physical report binding both physical streams. It records same-generation lineage, not independent connectivity verification. The resolver checks stream hashes before and after, validates full physical/component row agreement on every selected row, and requires each point to land inside exactly one physical-land component. Grid-line points, zero hits, duplicate feature IDs, duplicate or conflicting component claims, malformed sources, unselected decisions and changed files fail. Output claims carry the `affiliation_id`, both source identities and hashes, source geometry hash, target, island identity and resolved grid cell/component. This is designed for future renderer integration, but the current List 1 renderer cannot yet consume this trace; no production or draft decision has been registered.

## Run and tests

```
/usr/bin/python3 resolve.py request.json new-report.json
/usr/bin/python3 -m unittest -v test_adapter.py test_resolve.py
```

The output path must be outside every input file’s directory and must not already exist; a temporary file is atomically linked without overwriting. The request, snapshot, manifests and physical report are each limited to 8 MiB; raw point-source JSON is limited to 1 MiB. Point parsing requires at least 224 MiB of host headroom above the 1,730,151 KiB floor before and after parsing. The resolver code and request are pinned/rechecked, and all other file pins are rechecked. The process stops if Linux available memory falls below 1,730,151 KiB; tests mock this guard. Each selected row is discarded after use, and row offsets cannot request more runs than the grid width. Synthetic tests cover normal resolution and failures including bad pins, changed inputs, wrong geometry or point names, water/grid-edge points, malformed component rows, duplicate source features, duplicate component claims, and wrong component lineage. They do not prove real source custody or full-grid topology. No real source point has been selected in Neon or resolved by the integrated prototype. A separate read-only diagnostic checked two original Natural Earth source points against generalized identity-label polygons; it made no map or selection.

Source CRS must be absent (RFC 7946) or explicitly recognized as OGC CRS84. Nested CRS declarations on the selected feature or its geometry are rejected. Named-identity claim traces include both normalized CRS labels and `source_crs_scope: collection_feature_geometry`; this does not inspect unselected features.
