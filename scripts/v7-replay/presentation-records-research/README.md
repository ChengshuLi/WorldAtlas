# Historical review presentation research

This isolated code-only prototype moves release-specific island display records out of renderer branches and validates that a proposed export reproduces an independently pinned historical reference index. It does not change the current UI, publish a Site, install a database schema, or create Neon records.

`presentation_release_schema.sql` proposes one immutable historical-presentation row per release, with foreign keys to separately cataloged proposal, water-presentation and reference artifacts. The row is not an executable geography decision. The row-level and TRUNCATE triggers protect ordinary mutations; privileged owners can alter or disable them. Database constraints alone do not authenticate data, check canonical record bytes, or prove source geography.

`export_presentation_release.sql` is a parameterized, read-only query for an authenticated Neon connection. `verify_neon_presentation_export.py` compares the exported source IDs/versions, R2 keys, sizes and hashes against a caller-authenticated release manifest and independently read-back bytes, then checks canonical string-only JSONB records. It invokes `verify_presentation_release.py`, which rejects lossy JavaScript numeric inputs and compares both generated indexes to the pinned historical reference using lossless decimal semantics. This checker uses Linux sealed memfds and bounded pipes. It requires a trusted Python environment, Node executable and checker code; an origin string or local file hash does not authenticate Neon by itself.

`data-driven-review.mjs` is an isolated renderer variant, not a deployed replacement. `test_data_driven_review.mjs` uses fictional records. `test_verify_presentation_release.py` and `test_verify_neon_presentation_export.py` use synthetic files and mocked boundaries. Run those three tests from this directory with Node and Python. Separately, a local fixture using R2-readback historical bytes and a simulated Neon export reproduced the full index; that is not an actual Neon row or an authorization to deploy.

Before use: catalog exact source artifacts with accurate rights and provenance; install a reviewed schema under the project's migration process; authenticate and export the actual Neon row; pin the source and checker hashes in an independently trusted release manifest; recheck exact R2 readbacks and canonical records; test tampering, browser rendering, cache versioning and rollback on a staging deployment. Keep the current historic UI unchanged until full parity and coordinated release are established.
