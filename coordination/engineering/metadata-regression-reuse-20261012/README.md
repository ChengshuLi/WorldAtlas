# Known-program metadata regression reuse

Continuation of issue #1793 after the geography-only first increment. Avoid a
second full regression/build/package execution for a direct receiving-metadata
successor when an explicitly audited programme and authenticated successful
original execution establish unchanged inputs. Current acceptance remains fresh.

## Observed case

PR #1790 changed only the receiving README and evidence manifest between fe3b14d
and b1cc388. Its original run 38237899123 failed scope but passed geography,
three full regression shards and package. The longest original shard took
19 minutes 31 seconds. Scope failure does not erase successful computation and
does not supply ownership authority to the successor.

An offline replay of the exact complete original trees matches the retained
2,544-role programme vector and the two actual changed paths. This is a
retrospective applicability control under the new policy. Original trusted main
did not contain that policy, and the original PR is already merged; no live
reuse of that historical PR is claimed.

## Bounded admission

- Only a direct, single-parent successor with one or both issue-owned ordinary
  receiving README/evidence-manifest modifications is eligible. No additions,
  deletions, renames, mode changes or other changed files are admitted.
- The whole receiving directory must be absent from trusted PR base. Established
  evidence packets and workflow-copy roots cannot enter through this rule.
- A trusted-base catalogue must recognize the exact full test discovery and
  execution programme. It binds ordinary code/configuration namespaces,
  dependencies, policy selectors, and existing archived executable images.
  Unknown or changed readers use normal full execution. Programme equality
  alone is not a generic proof that arbitrary files are unused.
- Existing package-role exclusion and the complete audited scientific collector
  independently prove non-consumption of both changed files. Current, original,
  strict-history and fallback-presence identities remain necessary.
- Original full shards and package steps must actually have succeeded on the
  immutable original head/run/attempt. Failed or missing computation and a prior
  reuse-only run do not qualify. There are no recursive proof chains.

## Fresh controls and queue acceptance

The existing regression checkout and Node installation remain. An admitted head
runs job-deadline, supported-programs, selected-data-profile and
integration-profile-restoration directly, without canonical/model preparation
or another hosted build. The original measured four-file subset completed
240 controls in 52.514 seconds; that warm-fixture measurement is retained in the
first increment and is not a hosted latency promise.

Current profile, ownership, scope, evidence and exact-head independent review
remain required. Package acceptance explicitly identifies original successful
package verification and does not claim a newly built asset.

The queue reauthenticates the original computation and current control job
against actual main and the exact candidate tree, including after capacity
waiting and before merge. Source and current attempts retain separate identities.
The result supplies no transferable geography job or checkpoint authority, so the
queue performs its ordinary exact-candidate geography check. Existing accepted
checkpoint origin bytes and historical seed pins remain untouched.

Only immutable input collection can be cached within one queue process. Live PR,
issue, run, job, artifact and programme authority are reread. Cold routing-tree
reads use the current admitted/counting API. Admission exceptions retain their
budget/replanning metadata even when the scientific collector emits a fallback.

## Verification and limits

Focused controls exercise authentic scope-failed original job metadata, complete
programme identity, unknown readers, existing packets, altered trees/baselines,
failed/ambiguous producers, current-control failures and skips, source/current
reruns, queue final revalidation, immutable-only caching, request accounting and
safe budget replanning. Current checkpoint qualification uses the existing
accepted-seed entrypoint with body-open traps; it does not repeat old science.

The current catalogue descriptor changes only integration-proof.mjs in the
existing 17-role executing qualifier. Historical root/seed/archive bindings are
unchanged. The known current programme is independently qualified with a new
receiving-packet positive and unknown-reader, changed-test and old-packet negatives.

Actual subsequent hosted reuse and measured critical-path improvement remain
acceptance work. Unavailable proof, expired artifacts, changed baseline or an
unknown programme keeps normal full checks. No source approval, content import,
publication or live deployment is granted.
